# Kubernetes 部署策略指南

## 概述

Kubernetes 提供多种部署策略，帮助团队在生产环境中安全地发布应用更新。选择合适的策略取决于应用特性、风险容忍度和基础设施规模。

## 滚动更新（Rolling Update）

滚动更新是 Kubernetes 默认的部署策略。它逐步用新版 Pod 替换旧版 Pod，确保在更新过程中始终有一定数量的 Pod 可用。

关键参数：
- `maxUnavailable`：更新过程中允许不可用的最大 Pod 数量
- `maxSurge`：更新过程中允许超过期望副本数的最大 Pod 数量
- 建议将 `maxUnavailable` 设为 25%，`maxSurge` 设为 25%

适用场景：无状态应用的常规版本更新，对零停机时间有要求但允许短暂的版本混合状态。

## 蓝绿部署（Blue-Green Deployment）

蓝绿部署维护两套完全相同的生产环境。新版应用部署在"绿色"环境，验证通过后将流量从"蓝色"切换到"绿色"。

实现方式：
- 使用 Kubernetes Service 的 selector 切换流量
- 通过 Ingress 控制器实现流量切换
- 使用 Argo Rollouts 或 Flagger 进行自动化管理

优势：零停机时间、快速回滚（只需切换 Service selector）。
劣势：需要双倍的计算资源。

## 金丝雀发布（Canary Release）

金丝雀发布将少量流量导向新版本，逐步扩大新版流量比例。

实施步骤：
1. 部署新版 Pod，初始副本数设为 1
2. 通过标签选择器将 10% 流量导向新版
3. 监控新版的关键指标（错误率、延迟、CPU 使用率）
4. 按 10% → 30% → 50% → 100% 逐步扩大流量
5. 如发现问题，立即回滚到旧版

监控指标要求：
- 错误率不超过基线的 1.5 倍
- P99 延迟不超过基线的 1.2 倍
- CPU 和内存使用率在正常范围内

## A/B 测试部署

A/B 测试在生产环境中同时运行多个版本，根据用户特征（地理位置、浏览器类型、用户标签）分配流量。

与金丝雀发布的区别：
- 金丝雀关注发布安全性，A/B 测试关注功能效果
- A/B 测试通常运行更长时间（数天到数周）
- A/B 测试需要更精细的流量路由和数据分析

## 回滚策略

所有部署策略都应包含回滚计划：
- 自动回滚：基于健康检查和指标阈值自动触发
- 手动回滚：`kubectl rollout undo deployment/<name>`
- 回滚时间目标（RTO）：生产环境不超过 5 分钟
- 数据回滚：数据库迁移脚本必须支持向前和向后兼容
