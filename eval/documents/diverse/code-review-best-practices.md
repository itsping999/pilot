# 代码评审最佳实践

## 评审原则

代码评审是软件工程中最重要的质量保障环节。有效的评审不仅能发现缺陷，还能传播知识、统一代码风格、提升团队整体技术水平。

## 评审流程

### 提交前准备
- 作者应先自行检查代码，确保编译通过、测试通过
- 每个 Pull Request 的变更行数控制在 400 行以内
- 提交信息遵循 Conventional Commits 规范：`type(scope): description`
- 关联 Issue 编号，说明变更动机

### 评审重点
1. **正确性**：逻辑是否正确，边界条件是否处理
2. **安全性**：是否存在注入、越权、信息泄露等安全风险
3. **可维护性**：命名是否清晰，函数是否职责单一
4. **性能**：是否存在 N+1 查询、内存泄漏、不必要的锁竞争
5. **测试覆盖**：关键路径是否有单元测试，边界条件是否覆盖

### 评审时限
- 小型 PR（< 100 行）：4 小时内完成评审
- 中型 PR（100-400 行）：1 个工作日内完成评审
- 大型 PR（> 400 行）：建议拆分后再提交

## 评审反馈规范

### 评论分级
- `nit`：代码风格问题，不阻塞合并
- `suggestion`：改进建议，作者可自行决定是否采纳
- `issue`：必须修改的问题，阻塞合并
- `blocker`：严重问题，需要重新设计

### 反馈原则
- 对事不对人，聚焦代码而非作者
- 提供具体的改进建议，而非仅指出问题
- 区分"必须修改"和"可以改进"
- 肯定做得好的地方，保持积极的评审氛围

## 常见反模式

- **橡皮鸭评审**：只看格式，不看逻辑
- **完美主义评审**：追求代码完美而阻塞发布
- **延迟评审**：PR 提交后长时间无人评审
- **一次性评审**：大型 PR 一次审完，质量无法保证

## 工具辅助

- 静态分析：ESLint、Clippy、SonarQube 自动检查代码质量
- 自动格式化：Prettier、rustfmt 统一代码风格
- CI 集成：自动运行测试、覆盖率检查、安全扫描
- 代码所有权：CODEOWNERS 文件自动分配评审人
